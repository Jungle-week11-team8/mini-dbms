# 시나리오 3: API 서버 (Phase 3)

[← README](../README.md)

## 유저 스토리
- **누가**: 백엔드 개발자
- **무엇을**
  - API 서버로 데이터를 조회·삽입한다.
  - 여러 클라이언트가 하나의 DB를 써도 서로의 결과에 영향을 주지 않는다.
  - DB에서 오류가 나면 에러 메시지를 받는다.
- **왜**
  - CLI로 직접 타이핑하지 않고 요청을 자동화하려고
  - 데이터가 꼬이지 않고 원하는 결과를 얻으려고
  - 오류 원인을 알고 대응·디버깅하려고

## 완료 조건과 결과
| 완료 조건    | 결과 | 테스트                                            |
|----------| --- |------------------------------------------------|
| 조회·삽입    | `POST /query` ([매뉴얼](manual.md#api)) | `ApiServerTest`                                |
| 서로 영향 없음 | 테이블별 배타 락, `data/.lock` ([개념](concepts.md#3-동시성-phase-3)) | `ExecutorTest`: 8스레드 동시 INSERT에서 `_id` 중복·행 깨짐 없음 |
| 오류 메시지   | `{"error":"..."}` + 상태 코드 400/404/405/413/500 | `ApiServerTest`                                |


## 써 보며 느낀 점

### 좋았던 점
- **쉬운 사용**: 서버 실행이 쉽고, Postman 같은 도구에서 body에 SQL을 그대로 보내면 됩니다.

### 한계
- **터미널 응답 읽기 어려움**: curl로 받으면 응답이 한 줄 JSON이라 한눈에 읽기 어렵습니다.
- **같은 테이블은 한 번에 하나씩**: 배타 락이라 같은 테이블의 SELECT끼리도 동시에 실행되지 않습니다.
