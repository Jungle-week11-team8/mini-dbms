## 1. 저장 (Phase 1)
스키마 형식(JSON) 비교는 [README](../README.md#2-스키마-형식-json)에 있습니다.

### Phase 2를 미리 고려한 결정
- **타입을 스키마에 둠**: `WHERE age > 20`을 숫자로 비교하려면 타입 정보가 필요합니다. AI는 "CSV 헤더" 방식을 추천했지만, 타입을 담지 못해 채택하지 않았습니다.
- **다음 `_id`는 저장하지 않음**: 인덱스를 만들 때 데이터를 어차피 다 읽으므로, 그때 가장 큰 `_id`를 알 수 있습니다.

## 2. 인덱스 (Phase 2)

### B+ 트리
| 항목       | 결정                                                | 이유 |
|----------|---------------------------------------------------| --- |
| 노드당 최대 키 | 생성자 인자, 실제 사용값 128                                | 벤치마크에서 64 이상부터 큰 차이가 없음 |
| 최소값 검사   | 3 미만이면 오류                                         | 너무 작으면 분할 때 키 0개짜리 내부 노드가 생겨 균형이 깨짐 |
| 부모로 올릴 값 | 리프는 오른쪽 첫 키를 **복사**, 내부 노드는 가운데 키를 **이동**. 분할은 반반 | |
| 노드 저장    | `long[]` 고정 배열 + 개수                               | 고정 길이 키일 때 실제 DBMS 페이지를 메모리에서 단순화한 모양 |
| 리프의 값    | CSV **바이트 오프셋**                                   | 아래 표 |
| 중복 키     | 오류                                                | 버그를 바로 드러내기 위해 |
| 조회 결과 없음 | 빈 값 반환                                            | |

리프에 무엇을 적을지 세 가지를 비교했습니다.

| 후보 | 결과 |
| --- | --- |
| **바이트 오프셋** | 파일의 그 위치로 바로 점프해 한 줄만 읽음 |
| 줄 번호 | 줄 길이가 제각각이라 처음부터 줄바꿈을 세야 함. 인덱스 효과 없음 |
| 행 데이터 자체 | 가장 빠르지만 100만 행이 전부 메모리에 올라감 |

<br/>

### 인덱스 수명
- 인덱스는 메모리에만 두고, 실행마다 CSV를 훑어 다시 만듭니다.
- 그래서 조회가 1번뿐이면 이득이 없고, 조회를 여러 번 반복할 때 이득이 큽니다.
- 인덱스는 쿼리 실행 함수가 아니라 테이블 상태(`TableState`)가 들고 있습니다. 그래서 API 서버에서는 처음 한 번 만든 뒤 요청마다 재사용합니다.

<br/>

## 3. 동시성 (Phase 3)

### 왜 테이블 단위 락인가
- **테이블 락이 자연스러움**: 상태(인덱스, 다음 `_id`, CSV 파일)가 전부 테이블 이름으로 갈라져 있습니다. 그래서 테이블마다 락 하나로 같이 보호됩니다.
- **행 락은 의미가 적음**: INSERT만 있어서 한 번 쓴 행은 바뀌지 않습니다. 실제 충돌 지점은 행이 아니라 B+ 트리 구조 전체입니다.

<br/>

### 배타 락 VS 읽기/쓰기 락
- **읽기/쓰기 락**: SELECT가 많을 때 성능이 좋지만 고려할 점이 많습니다. 예를 들어 첫 SELECT가 인덱스를 만들며 상태를 바꾸는데, 읽기 락을 쥔 채 쓰기 락을 요청하면 데드락이 납니다.
- **선택**: mini-DBMS인 점과 시간을 고려해 처리할 것이 적은 **배타 락**을 골랐습니다. 락을 잡는 곳이 한 군데라 나중에 바꾸는 비용은 작습니다.

<br/>

### 테이블 락의 한계와 보완
1. **공유 맵**: 서로 다른 테이블 락을 잡은 두 스레드가 같은 `HashMap`에 동시에 `put`할 수 있었습니다. 락은 같은 락을 잡는 스레드끼리만 막아 줍니다.
   → `ConcurrentHashMap`으로 바꿨습니다.
2. **첫 조회의 쓰기**: 첫 `SELECT WHERE _id`도 인덱스를 만들면서 상태를 바꿉니다. 해결 방법 4가지를 비교했습니다.
   - 서버 시작 때 미리 만들기
   - 확인도 락 안에서 하기
   - `synchronized` 메서드
   - `computeIfAbsent`

**우리 코드**
- `computeIfAbsent`로 테이블 상태(`TableState`)를 테이블당 하나만 만듭니다. 스키마가 있는 테이블만 만듭니다.
- 인덱스 만들기, CSV 쓰기, 다음 `_id` 예약은 그 객체의 배타 락(`synchronized`) 안에서 처리합니다.

<br/>

### 프로세스 사이 충돌
- 스레드 락은 한 프로세스 안에서만 효과가 있습니다.
- 서버 실행 중 CLI가 `data/`에 쓰면, 서버는 그 행을 모릅니다. 인덱스로 찾지 못하고 `_id`가 중복될 수 있습니다.
- 그래서 서버와 CLI 둘 다 `data/.lock`(OS 파일 락)을 잡고, 못 잡으면 바로 종료합니다. 이 락은 프로세스가 죽으면 자동으로 풀립니다.

| 단계 | 누가 지키나 |
| --- | --- |
| 인덱스, 다음 `_id`, CSV 쓰기 | 테이블별 배타 락 |
| JSON 변환 | Gson (스레드 안전, 하나를 공유) |
| 다른 프로세스와의 충돌 | `data/.lock` |

<br/>

### API를 이렇게 정한 이유
- **JDK `HttpServer`**: 스레드 풀을 직접 설정할 수 있습니다.
- **엔드포인트 1개**: 기존 Parser를 그대로 재사용합니다.
- **대기열**: 크기 제한 없음. 다만, 요청이 끝없이 몰리면 대기열이 계속 커져서 메모리 사용량이 계속 늘어날 수 있습니다.
- **400과 500 구분**: 요청이 잘못된 것인지(400), 서버 쪽 디스크 문제인지(500)를 나눕니다.
