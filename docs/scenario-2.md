# 시나리오 2: 인덱싱 (Phase 2)

[← README](../README.md)

## 유저 스토리
- **누가**: DBMS 관리자, 데이터 관리자, 백엔드 개발자
- **무엇을**: 
  - 대규모 데이터(최소 100만 건)에서도 원하는 데이터를 빠르게 찾는다. 
  - 선형 조회 대신 인덱스로 탐색 시간을 줄인다.
- **왜**: 
  - 대용량 데이터는 흔한데, 매번 순차 탐색하면 조회가 오래 걸립니다. 
  - 배치 작업에서 건별 조회가 수십만 번 반복되면 지연이 누적됩니다.

## 완료 조건과 결과
| 완료 조건                     | 결과 |
|---------------------------| --- |
| B+ 트리 자료구조 생성             | `index/BPlusTree` ([설계](design.md#2-인덱스-phase-2)) |
| 자동 부여된 `_id`를 인덱스에 자동 등록  | INSERT 때 CSV에 쓴 뒤 트리에 등록 |
| `_id` 탐색에 B+ 트리 적용        | `WHERE _id = n`이 자동으로 인덱스를 탐 |
| 대규모 데이터로 인덱싱과 선형 탐색 속도 비교 | `./gradlew bench` (아래) |

인덱스 대상은 `_id`로 고정했습니다. 사용자가 원하는 컬럼에 인덱스를 거는 방식은 하지 않았습니다.

<br/>

## 벤치마크 결과 (100만 행, 팀원 3대 머신)
| 항목 | 머신 1 | 머신 2 | 머신 3 |
| --- | --- | --- | --- |
| 조회 1건: 인덱스 | 0.38 ms | 0.035 ms | 2.0 ms |
| 조회 1건: 선형 INT | 456 ms | 155 ms | 732 ms |
| 인덱스 / 선형 INT | 1,196배 | 4,420배 | 361배 |
| 재구축 비용 회수 | 조회 2.0번 | 1.0번 | 0.9번 |

**공통 결론**
- 인덱스가 선형 조회보다 수백 배 이상 빠릅니다.
- 재구축 비용은 조회 1~2번이면 회수됩니다.
- 노드당 최대 키는 4가 가장 느리고, 64 이상부터는 큰 차이가 없습니다.

<br/>

## 써 보며 겪은 한계
- **머신마다 차이가 큼**: 
  - 인덱스 조회와 INSERT 시간이 머신마다 수십 배 차이 났습니다. 
  - 선형 탐색(약 5배)보다 훨씬 큽니다. 
  - 두 작업 모두 호출마다 파일을 열고 닫는 구조라서 그런 것으로 추정합니다.
- **조회가 1번뿐이면 이득 없음**: 실행마다 인덱스를 다시 만들기 때문입니다.
